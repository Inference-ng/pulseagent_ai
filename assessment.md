What's Still Wrong ❌
faiss-cpu and sentence-transformers are still unpinned. Every other critical package now has a version. These two don't. sentence-transformers has had breaking changes across major versions, and faiss-cpu has platform-specific build variants. If a judge builds fresh and gets a different version, the embedding dimensionality or API could break. Minimum fix: faiss-cpu==1.7.4 and sentence-transformers==2.7.0.


The langchain==0.2.0 + langchain-google-genai==1.0.5 pin is a version conflict. langchain-google-genai==1.0.5 internally requires langchain-core>=0.1.28,<0.2. But langchain==0.2.0 ships with langchain-core==0.2.x. These two will fight during pip install and one will get downgraded. The actual package that matters for Emmanuel's code is langchain-google-genai and langgraph — he doesn't use langchain or langchain-community directly anywhere in his agent files. Pinning langchain==0.2.0 and langchain-community==0.2.0 causes a conflict for no benefit. The cleaner fix is to remove those two and let the transitive deps resolve naturally.
ReviewResult is still in schemas/models.py but never used anywhere. The schema defines it, but no agent imports or validates against it. It's dead schema. Not a bug, just unused code that a judge reading the schemas will notice.
The FAISS domain filter has a case mismatch that will silently fail for most queries. In retrieve(), the domain filter compares r.get("category", "").strip().lower() == domain where domain has already been lowercased. But the CSV categories are title-case: "Fashion", "Electronics", "Books", "Food". After lowercasing both sides this works — but the fallback then checks if len(filtered) < top_k and uses unfiltered results. For domain="books" with a catalog containing "Books", it will match correctly. However for domain="food" it will match "Food" correctly too. Actually this specific logic is fine — both sides are .lower()-ed. But VALID_DOMAINS = ["fashion", "electronics", "books", "food"] doesn't include "restaurants" or "beauty" — which exist in the FAISS index. Users cannot request those domains through the API even though the data exists. Minor gap but worth noting.

The simulate.py router passes req.user_persona.model_dump() to the agent — but the agent expects price_sensitivity as a required field. UserPersonaRequest has price_sensitivity: Optional[str] = "medium". When .model_dump() is called, if the caller doesn't send price_sensitivity, it defaults to "medium" and gets passed through. That's fine. But UserPersona in schemas/models.py (Emmanuel's schema) has price_sensitivity: Literal["high", "medium", "low"] as a required field with no default. If the backend sends "medium" as a string, it's valid. No mismatch here — this actually works. But the two schema files defining the same structure in two different places is fragile long-term.
The backend Dockerfile still runs prisma generate but never runs prisma db push or prisma migrate deploy. The SQLite database file doesn't exist at build time. When the container starts and connect_db() is called, it will fail because there's no schema applied to the SQLite file. The startup falls back gracefully, so the API still works — but the database is never actually initialized. A CMD hook or an entrypoint that runs prisma db push before uvicorn would fix this. Right now, anyone trying to use the database logging will get nothing, silently.


The backend tests use @patch decorator without async test functions. Both test_simulate_review_endpoint and test_recommend_endpoint are plain def functions, not async def. The AsyncMock is set up correctly, but the TestClient from FastAPI/Starlette runs the app synchronously in tests anyway, so this will likely work. But it's inconsistent — if anyone adds pytest-asyncio style async tests later, the pattern won't carry over cleanly.
context_query is Optional[str] defaulting to "" in RecommendRequest, but the agent treats an empty string differently from None. In retrieve(): query = state.get("context_query", "").strip() — if it's "", it falls back to category names. This is correct behaviour. But the frontend README and API docs show context_query as a regular field. If a caller sends context_query: null, Pydantic will coerce it to "" due to the Optional[str] = "" default. No bug, but slightly surprising API contract.
