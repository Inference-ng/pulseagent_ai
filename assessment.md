Emmanuel's Work (AI Agent) — Honest Assessment
What's genuinely good
The LangGraph state machine is well thought out. The four-node pipeline (retrieve → contextualize → generate → validate) is clean, each function has a single clear responsibility, and the graph is wired correctly. The lazy FAISS import inside retrieve() to prevent a Windows DLL segfault is a real engineering decision, not cargo cult code — whoever thought of that knows what they're doing.
The FAISSStore class is solid: graceful empty-index fallback, clean add_items / search / save / load interface, correct dimensionality (384 for all-MiniLM-L6-v2), and proper HuggingFace auth patching. The cold-start 3-step fallback in the recommendation agent is thoughtful and directly targets 25 scoring points.
The verify.py script is genuinely impressive — it's a self-contained pre-flight audit with clear error messages, fix instructions, and a clean pass/fail summary. That kind of developer experience thinking is rare in hackathon code. The manual_test.py is also well-written, with a Windows-safe safe_print() function and the FAISS pre-warm before LLM imports.
The Nigerian context layer in the prompts is natural and not forced. The synthetic product catalog in loader.py is rich, covering fashion, electronics, books, food, beauty, and restaurants — with authentic Nigerian cultural references throughout (Slot, Jumia, Konga, NEPA, owambe, garri). The data pipeline (loader → embed) is cleanly separated.
The Pydantic schemas in schemas/models.py are clean and properly typed.
The real problems
base_agent.py is a stub. It contains only def get_base_workflow(): pass. It's imported nowhere and does nothing, but it sits in the repo looking like incomplete work. Either implement it or delete it.
user_memory.py is a stub. Same problem — def build_user_memory(user_id, purchase_history): pass. The solution paper claims FAISS user memory for Task A, but the actual retrieve() node in user_modeling_agent.py just reads purchase_history from the input dict — no FAISS involved. The paper and the code are out of sync on this point.
The FAISS index is not committed. data/processed/ is empty. This is the single biggest functional gap. Without running loader.py then embed.py, Task B's retrieval returns an empty list and the whole ranking pipeline falls back to fabricated items. The synthetic catalog in loader.py is good — the pipeline just needs to be run and the output files committed.
The contextualize node does nothing. It's literally return state. It exists as a graph node but adds zero logic. Either remove it from the graph or give it real work (e.g., building a rich NL context string like the solution paper describes — "Emmanuel is a price-sensitive Lagos shopper..."). Right now it's padding.
The cross-domain injection is hardcoded to "Books & Education" regardless of what domain the user is in. A fashion user gets a Books cross-domain. A Books user also gets a Books cross-domain — which isn't cross-domain at all. It needs simple logic to pick a different domain from the user's current one.
The ai-agent Dockerfile's CMD is wrong. It runs python -c "print('AI Agent module ready')" and exits immediately. The container starts, prints one line, and dies. Since the backend mounts the ai-agent as a volume and imports it directly, the container doesn't need to stay running — but this CMD will confuse anyone trying to understand the architecture. It should at least run verify.py or a health check.
The Task B prompt file (task_b_prompt.py) is never used. TASK_B_SYSTEM_PROMPT and TASK_B_HUMAN_PROMPT are defined in the file but the actual prompts in recommendation_agent.py are written inline as f-strings. Either use the prompt module or remove the file — having both is confusing.
Duplicate entries in loader.py. Books items b001–b005 appear twice in the synthetic catalog (once in the main list, again later). This means the FAISS index will have duplicate vectors for those items, inflating search hit counts.

Nwokedi's Work (Backend) — Honest Assessment
What's genuinely good
The FastAPI structure is properly layered — routers, services, schemas, utils, all in the right places. The agent_service.py bridge is the right pattern: it wraps Emmanuel's synchronous LangGraph agents in a ThreadPoolExecutor so they don't block the async event loop. That's not obvious and it's done correctly.
Both routers (simulate.py, recommend.py) have proper timeout handling with asyncio.wait_for, domain validation, response structure validation, background task logging, and correct HTTP status codes (504 for timeout, 422 for bad domain, 500 for agent errors). This is genuinely solid production-grade FastAPI code for a hackathon.
config.py using pydantic-settings with a cors_origins_list property is clean. The Prisma schema is well-normalised with proper indexes on all foreign keys and query fields, and the AuditLog model is a thoughtful addition. The requirements are pinned to exact versions — good for reproducibility.
The docker-compose.yml is now fixed (was purseagent before, now correctly pulseagent), and the GOOGLE_API_KEY is correctly passed to the ai-agent service.
The real problems
db_service.py will crash silently on every call. The startup_event in main.py explicitly says "Running in database-less mode" and never calls connect_db(). But db_service.py calls prisma.user.upsert(...), prisma.simulation.create(...) etc. on an unconnected Prisma client. These calls will throw exceptions every time — they're swallowed by the except Exception as e: print(...) blocks, so the API won't crash, but every background log task silently fails. This is fine for the hackathon demo but it's technically broken infrastructure.
agent_service.py has a duplicated exception handler. In run_task_b, the except ImportError and except Exception blocks appear twice at the end of the function. This is dead code — the second pair can never be reached. It looks like a copy-paste error that was never cleaned up.
The backend Dockerfile runs prisma generate but there's no database. The DATABASE_URL defaults to a SQLite connection string in docker-compose, but the Prisma schema specifies provider = "postgresql". prisma generate will succeed, but prisma migrate was never run and won't work with SQLite. This is consistent with the database-less mode decision in main.py, but it means the Dockerfile has a step that generates a client for a database that will never be connected.
RecommendRequest doesn't include context_query. The request schema has user_persona, top_k, and domain — but no context_query field. In agent_service.py, run_task_b calls get_recommendations(user_persona, top_k, domain, "") — hardcoded empty string. So the conversational/context-query feature (which is part of the scoring) is never passed from the API. A frontend user typing "I want shoes for owambe" into a context field would have that query ignored entirely.
Backend tests are shallow. test_simulate.py just checks that the endpoint exists and accepts status codes 200, 501, or 422. test_recommend.py is the same. Neither test actually validates a correct response. The comment "Will not be implemented until Phase 6" is still in the test files — Phase 6 clearly happened (the agent service is implemented), but the tests were never updated to match.
